Locally implemented, unregistered and not deployed. Parent integration owns registration/release. Private local inputs only; zero model/search/context/live calls, no Slack identity lookup, jobs, workflows or external changes.

```

```

Use the full returned process, review-step and token IDs. Baseline analysis gives 35 active + 180 waiting = 215 sequential elapsed minutes, one adjacent-owner handoff, and 140 active/720 wait/860 elapsed monthly minutes at four occurrences. The review step accounts for 66.67% of entered wait (rounded). Changing only its wait assumption to 30 gives 35 active + 90 wait = 125 elapsed. Preview and saved scenario leave baseline steps unchanged. Inspect the pending assumption before copying the exact save command; token is consumed once.

Time inputs are nonnegative decimals ≤1,000,000 minutes with at most three fractional places. Internally active/wait/largestWait are exact integer thousandths of a minute; exported JSON and preview explain these units. Monthly repetitions are integers 1–10,000. Bounded sums/products remain safe integers. Analysis assumes sequential nonoverlapping steps, does not equate waiting reduction to labor/cloud savings, and makes no guaranteed savings claim. Handoffs count adjacent unequal nonempty owner labels; unknown boundaries are excluded. Largest-wait ties use first step. Zero total wait gives undefined share, not division by zero.

`what-if PROCESS STEP | active|wait|owner|remove | VALUE` changes exactly one assumption (choose one field). For removal, VALUE is replacement rationale; it must be nonempty when the baseline step has a required reason. This is a paper scenario, not execution. Up to three explicitly saved scenarios retain their changed-step snapshot, exact numerical before/after comparison, baseline identity/revision/fingerprint and name. They do not retain a full historical graph. Saved names use `scenario-name PROCESS SCENARIO | NAME` / `scenario-clear-name PROCESS SCENARIO confirm`. `revise PROCESS SCENARIO STEP | FIELD | VALUE` creates a replacement preview against the current baseline; reviewed save replaces every prior snapshot/assumption while preserving the scenario ID. To edit source snapshot fields, edit baseline input then explicitly revise. `scenario-remove PROCESS SCENARIO confirm` erases all retained scenario fields; `discard PROCESS confirm` erases the pending preview.

Maintain baseline with `edit PROCESS | title|repetitions | VALUE`, `clear PROCESS title confirm`, `step PROCESS edit STEP | label|active|wait|ownerLabel|requiredReason | VALUE`, and `step PROCESS clear STEP label|ownerLabel|requiredReason confirm` (choose one field). Numeric zero is an explicit edit; removing a step removes required numerical fields. `none` denotes no required reason only on step creation. `move PROCESS STEP | POSITION` uses 1-based order; `step PROCESS remove STEP confirm` explicitly removes baseline input. Every baseline edit issues a fresh immutable baseline ID, discards pending preview and marks saved scenarios historical—even an edit back to old content cannot restore previous review status. Existing historical comparisons remain truthful, labelled summaries until revised or removed.

`list [PAGE]`, `show PROCESS [PAGE]`, `export PROCESS` and `delete PROCESS confirm` cover complete retrieval and root erasure. Show/export include all input/snapshot/preview fields. Emitted continuations bind revision plus complete-content hash and preserve atomic IDs/hashes/URLs. Normal pages ≤3,500 JavaScript units; export envelope ≤24,576 serialized UTF-8 bytes. Static metadata help contains exact grammar. Pipe fields trim outer whitespace; `\|` / `\\` preserve literal pipe/backslash.

Limits: 12 processes, 24 ordered steps, three saved scenarios and one pending preview/process. Title/step label/scenario name 160, owner 128, reason/rationale 320 UTF-8 bytes. Commands ≤16,000 bytes; state/content limits 49,152/32,768 serialized bytes. Admission dynamically reserves every saved scenario slot plus replacement preview, maximal final names/escaped rationale, largest changed-step snapshot, and numeric/revision growth. Empty baselines reserve only existing historical scenario names until a step is admitted. Counts and bytes can bind differently; no silent eviction or reset.

All mutation intent is captured before retryable CAS and checked against the complete target each retry. Same-root changes/deletion defeat stale save; unrelated roots retry safely. All non-erasure writes refuse at record revision 999,999,999. There is no collection/assessment counter or recycled ID; full-content stamps and fresh baseline UUIDs prevent content/review ABA. Read/export/confirmed erase remain available. Fully validated individually exportable legacy aggregates can be reduced through exact whole-root deletion without changing retained records or projections; ordinary writes retain all gates. Current and historical numerical summaries/enums are validated, malformed raw bytes are preserved, and backend exceptions are sanitized with inspect-before-retry wording for ambiguous saves.
